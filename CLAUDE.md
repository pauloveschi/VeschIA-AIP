# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
bun install          # install deps (bun.lock is the committed lockfile — see caveat below)
bun run dev           # vite dev — starts the TanStack Start app
bun run build         # vite build
bun run lint          # eslint .
bun run format        # prettier --write .
npx tsc --noEmit      # type-check (no dedicated script in package.json — run tsc directly)
```

- **There is no test suite** (no test runner in `devDependencies`, no test script). Don't assume Jest/Vitest exists.
- **`npm`/`npx` vs `bun`**: the repo's lockfile is `bun.lock`; `package-lock.json` is gitignored because it's an npm-install byproduct, not the source of truth. Prefer `bun run <script>`, but `npx tsc` for type-checking is fine and common since there's no bun-native equivalent needed.
- `bunfig.toml` enforces a 24h supply-chain guard on new package versions (`minimumReleaseAge`). Only `@lovable.dev/vite-tanstack-config` is excluded. Don't add more excludes without asking the user first (the comment in the file says so explicitly).
- To change the DB schema: use the Supabase MCP tools against project `tllrmyghikcysxfatbww` (see `supabase/config.toml`). `supabase/migrations/` only holds a README — migrations are applied live via MCP during development, not tracked as SQL files in this repo. After any schema change, regenerate `src/integrations/supabase/types.ts` (via the MCP `generate_typescript_types` tool) so `Tables`/`TablesInsert`/`TablesUpdate` stay accurate.

## Architecture

### What this is
VeschIA AIP is a multi-tenant SaaS automating corporate approval workflows across six "products" (`src/lib/empresa.tsx`: `aiprocont`, `aiprorh`, `aiprofin`, `aiprocomp`, `aiprojur`, `aiprocomer`). Routing is `/$produto/$empresa/...` — `$produto.tsx` validates the product slug, `$produto.$empresa.tsx` resolves the tenant (`empresas_clientes` row) by slug, checks its `status` (`trial`/`ativo` block-if-not), and wraps children in `EmpresaProvider`. Everything under that layout calls `useEmpresa()` / `useProdutoAtual()` for tenant context — both throw if called outside that route subtree, so components meant to be reusable across tenant and non-tenant contexts can't rely on them.

Separately, `/auth` + `/superadmin` is the **platform-level** surface (VeschIA staff managing client companies, gated by `profiles.is_super_admin`), distinct from `/$produto/$empresa/auth` which is **tenant member** login. Don't conflate the two auth surfaces.

### Generated files — do not hand-edit
These are regenerated by tooling (Supabase/Lovable codegen) and say so in their own header comment:
- `src/integrations/supabase/{client.ts,client.server.ts,types.ts,auth-attacher.ts}` and `src/integrations/supabase/auth-middleware.ts`
- `src/routes/routeTree.gen.ts` (TanStack Router's file-based route tree)

If one needs a real change, regenerate it via the proper tool (Supabase MCP for types, the router plugin for the route tree) instead of editing by hand.

### Vite config is owned by Lovable
`vite.config.ts` is a thin wrapper around `@lovable.dev/vite-tanstack-config`, which already bundles `tanstackStart`, `viteReact`, `tailwindcss`, `tsConfigPaths`, the Cloudflare build plugin, dev-only component tagging, `VITE_*` env injection, the `@` alias, React/TanStack dedupe, error logger plugins, and sandbox port/host/strictPort detection. **Adding any of those plugins manually duplicates them and breaks the build.** Extra Vite config goes through `defineConfig({ vite: { ... } })`.

### Dual deploy target
The app ships to both Vercel (`vercel.json` — daily cron at `/api/rotina-diaria`) and Cloudflare Workers (`wrangler.jsonc`, `nodejs_compat`, `@cloudflare/vite-plugin`). `vite.config.ts` redirects TanStack Start's server entry to `src/server.ts`, which wraps the real handler for both targets. Any change to the server entry path needs to keep working under both runtimes.

### Error handling is layered on purpose
- `src/start.ts` registers a global `requestMiddleware` that catches server errors and renders a branded HTML error page (`src/lib/error-page.ts`) unless the error carries a `statusCode` (those are intentional HTTP errors and are rethrown).
- `src/server.ts` wraps the whole SSR fetch handler again, because h3 (TanStack Start's server) sometimes swallows an in-handler throw into a generic `{"unhandled":true,"message":"HTTPError"}` 500 JSON response that never reaches a `try/catch`. `normalizeCatastrophicSsrResponse` detects that exact shape and converts it into the same branded error page, recovering the real error from `src/lib/error-capture.ts` (a global `error`/`unhandledrejection` listener with a 5s TTL) for logging.
- If you introduce a new server entry point or bypass `src/server.ts`, you lose this safety net silently — SSR crashes will render as a raw JSON blob instead of the branded page.

### Supabase: two clients, different trust levels
- `src/integrations/supabase/client.ts` exports `supabase` — anon key, RLS-enforced, safe for browser and route components.
- `src/integrations/supabase/client.server.ts` exports `supabaseAdmin` — service-role key, **bypasses RLS**. Its own header comment is the rule: "Top-level import is safe only in other `.server.ts` modules — route files and `*.functions.ts` ship to the client bundle." Always load it with a dynamic `await import("@/integrations/supabase/client.server")` **inside** a `createServerFn().handler()` or a route's `server.handlers`, never as a top-level import in a `.tsx` route file, or the service role key's usage surface grows into client-shipped code.
- Auth propagation for server functions: `attachSupabaseAuth` (client-side `functionMiddleware`, registered in `src/start.ts`) attaches the user's bearer token to every `createServerFn` call automatically. `requireSupabaseAuth` (function middleware) validates that token server-side via `getClaims` for functions that need an authenticated caller. Don't hand-roll auth header plumbing — use these.

### Multi-layer authorization
Three independent checks compose for any tenant action, each with its own hook in `src/lib/empresa.tsx`:
1. **Membership + role** — `membros` table, `useMyEmpresaRole()` → `owner | admin | staff`, surfaced as `useIsEmpresaAdmin()` / `useIsEmpresaStaff()`.
2. **Product entitlement** — `empresa_produtos` table, `useProdutoContratado()` (has this empresa actually bought this product).
3. **RLS** at the Postgres level for anything going through the anon `supabase` client.

None of these substitute for the others — a route can be "in scope" (right product, right empresa) while the user still lacks the role or the entitlement.

### The workflow engine (`src/motor.server.ts`)
`avancarFluxo(admin, solicitacaoId)` is the state machine that drives a `solicitacoes` row through its `etapas_execucao` (ordered by `configuracao_fluxo`). It's called after every state-changing event (creation, an approval, a negotiation closing) and is **idempotent** — safe to call repeatedly, each action checks whether it already happened before doing it (e.g. contract creation catches Postgres `23505` as "already done, not an error"). Step semantics:
- `responsavel_tipo: "papel"` or `"ia"` → sends a one-shot email (via Resend, `avisarResponsavel`) with a token link, then stops and waits.
- Steps in `ETAPAS_CONTINUAS` (`Execução`, `Monitoramento`) never auto-complete — only the passage of time (the daily cron, see below) resolves them.
- Everything else is a "system step" and executes inline (e.g. `Elaboração do Contrato` calls `minuta.server.ts`, `Cadastro do Contrato` calls `executarCadastroContrato`).
- `reconciliarAprovadoresPorValor` runs on every invocation because `solicitacoes.valor` is `null` until the negotiation step sets it — approval-by-value-range steps must be re-resolved once the value exists, without touching steps already decided.
- `src/rotina.server.ts` + `src/routes/api.rotina-diaria.ts` (called once a day by the Vercel cron, guarded by a `CRON_SECRET` bearer check) is the mechanism that revisits the continuous-tracking steps that `avancarFluxo` can't close on its own.

### Token-based external access ("the link is the credential")
Several routes (`aprovacao.$token.tsx`, `juridico.$token.tsx`, `renovacao.$token.tsx`, `negociacao-externa.$token.tsx`) let someone act on a `solicitacao` **without logging in**, authenticated only by a random token in the URL, validated against `aprovacao_tokens` (`tipo` discriminates the flow: `"decisao"` = single-use, 7-day approve/reject-style tokens; `"trabalho"` = reusable, 30-day tokens for steps where the person needs to actually do work in the system, e.g. registering negotiating suppliers). Each route re-implements its own `resolverToken`-style validation against `supabaseAdmin` (no shared helper) — when touching one of these flows, check the sibling routes for the same pattern rather than assuming shared logic exists.

Each of these server functions returns a loosely-`estado`-tagged result to the client — when a route's success/error shapes genuinely differ in what fields they carry (see `negociacao-externa.$token.tsx`'s `carregarContexto`), model it as an explicit discriminated union (`{ ok: true; ... } | { ok: false; erro: ... }`) rather than one object with optional fields, so the client's guard `if`s let TypeScript narrow instead of needing non-null assertions.

### `*.server.ts` naming convention
`eslint.config.js` explicitly forbids importing the `server-only` npm package and tells you why: TanStack Start doesn't use Next.js's convention — server-only modules here are named `*.server.ts` (or marked with `@tanstack/react-start/server-only`). `motor.server.ts`, `minuta.server.ts`, `pdf-simples.server.ts`, `rotina.server.ts`, `client.server.ts` all follow this; anything without the suffix is assumed bundleable to the client.

### Data fetching: no repository layer
Components and routes call `supabase.from(...)` (or `supabaseAdmin` inside server functions) directly inside TanStack Query `useQuery`/`useMutation` — there's no service/repository abstraction to look for. Shared UI that needs to work in both an authenticated-direct context and a token-authenticated server-fn context takes an **`api` object as a prop** (see `PainelNegociacao`/`NegociacaoApi` in `src/components/negociacao-painel.tsx`): the internal route wires it to `supabase` directly, the external token route wires the same interface to `createServerFn`-wrapped calls. When extending a shared panel like this, update the interface and both call sites together.

### Typing Supabase insert/update payloads
Don't type a row going into `.insert()`/`.update()` as `Record<string, unknown>` — it defeats Postgrest's excess-property checking against the generated schema. Use the `Tables<"table">` / `TablesInsert<"table">` / `TablesUpdate<"table">` helpers exported from `src/integrations/supabase/types.ts`. Where a payload crosses a real runtime boundary with loose validation (e.g. a `createServerFn` input schema declared as `z.record(z.string(), z.any())` for a token-authenticated route), a payload from that field will still need an explicit type assertion at the point it's written to the DB — that's a legitimate trust-boundary cast, not something to "fix" by loosening the DB-side type back to `any`/`unknown`.

### Conventions to keep, not "fix"
- `tsconfig.json` has `noUnusedLocals`/`noUnusedParameters` off, and `eslint.config.js` turns off `@typescript-eslint/no-unused-vars` — deliberate, not an oversight.
- The codebase (identifiers, comments, table/column names, UI copy) is written in Brazilian Portuguese. Match that when adding code, including comments explaining non-obvious "why".
- `components.json` (shadcn/ui, "new-york" style) and Tailwind v4 (`src/styles.css`, `@theme inline` mapping CSS custom properties like `--color-primary` to utilities like `bg-primary`) define the design system. A few places set `style={{ background: "var(--primary)" }}` directly instead of a utility class — that's intentional where the utility class isn't available inline (e.g. dynamic values), not a pattern to "clean up" into Tailwind classes wholesale.

## Regras de negócio do fluxo AIProCont

O AIProCont ("Modelo Empresarial Padrão") é o produto mais maduro e o que exercita o motor (`src/motor.server.ts`) de ponta a ponta. As regras abaixo vieram de decisões de produto explícitas — registradas aqui pra não serem revertidas por engano numa sessão futura que só olhe o código e ache que é bug ou limitação a corrigir.

### As 11 etapas

A ordem vem de `configuracao_fluxo` (por empresa/produto) e é o que o motor percorre:

1. **Solicitação da Contratação** — só título, descrição, área, centro de custo. Sem valor nem fornecedor ainda (isso é o que faz `reconciliarAprovadoresPorValor` ser necessário — ver seção de arquitetura acima).
2. **Análise da Solicitação** — Gestor decide por token, sem login.
3. **Negociação Comercial** — Negociador cadastra empresas participantes (CNPJ/CPF validado, CEP via ViaCEP) e escolhe uma com justificativa obrigatória; as demais viram `descartada` mantendo histórico. É aqui que `solicitacoes.valor` passa a existir.
4. **Elaboração do Contrato** — IA (Gemini) gera a minuta em PDF e salva no Storage.
5. **Validação Jurídica** — ver sub-seção abaixo. Entrou nesta posição depois que o fluxo já tinha 10 etapas; todo o resto foi renumerado uma casa acima.
6. **Aprovação Interna** — Gestor sozinho até R$ 50 mil; Gestor **e** Diretor acima disso. O e-mail mostra a justificativa da negociação e as empresas descartadas com valores, pra quem aprova enxergar a comparação que sustentou a escolha.
7. **Assinatura** — simulada por enquanto; integração real (ZapSign/Clicksign/DocuSign) fica pra quando fechar o primeiro cliente pagante, porque todas são pagas.
8. **Cadastro do Contrato** — popula `contratos` automaticamente (`executarCadastroContrato`).
9. **Execução** — etapa contínua, não é o motor quem encerra.
10. **Monitoramento** — idem.
11. **Renovação ou Encerramento** — ver sub-seção abaixo.

A rotina diária (`src/rotina.server.ts` + `/api/rotina-diaria`) é quem detecta o vencimento, fecha Execução/Monitoramento e ativa a Renovação — não o motor.

### Validação Jurídica

Acesso por link/token, sem login, mesmo padrão de Gestor/Diretor/Negociador. Dois caminhos:

- **Aprovar** → segue pra Aprovação Interna.
- **Pedir ajuste** → campo de ressalva **obrigatório**, grava em `solicitacoes.ressalva_juridica`, reabre a Elaboração do Contrato (a IA regera a minuta injetando a ressalva no prompt e depois a ressalva é consumida/zerada), e a etapa volta pro Jurídico validar de novo.

Decisão fechada: **toda correção jurídica centraliza na Elaboração do Contrato** — seja cláusula, valor, data ou objeto — e **não existe caminho de volta pra Negociação**. O Negociador não tem repertório jurídico pra redigir cláusula; quem redige é a IA. **Sem limite de tentativas**: o ciclo Elaboração ↔ Validação Jurídica se repete quantas vezes for preciso. O Negociador só é notificado por transparência quando isso acontece, não precisa agir.

### Renovação ou Encerramento

- **Renovar** — reabre o ciclo com as mesmas condições: calcula o fim real do ciclo atual (início + vigência cheia), começa o novo no dia seguinte, aplica a regra dos 30 dias pra nova `data_termino`, volta o contrato pra `ativo`, zera `renovacao_ativada_em`/`alerta_previo_enviado_em`, e reabre Execução, Monitoramento e a própria etapa de Renovação.
- **Encerrar** — fecha o contrato (`status = encerrado`) e conclui a etapa.
- Em ambos os casos, **os tokens antigos da etapa são apagados** — senão o motor acha que "já avisou" nesse ciclo e não manda e-mail no próximo.
- Decisão fechada: **renovar repete os mesmos termos do contrato**, por enquanto — não é bug, é escopo consciente. Renovação com condições diferentes (prazo, valor, objeto, garantias distintos) depende do TAC (Termo Aditivo Contratual), que ainda não existe como funcionalidade.

### Decisões de produto já fechadas (não reabrir sem discutir com o usuário)

- **Etapa pendente sempre trava as seguintes**, obrigatória ou não. Etapa opcional tem botão "Pular etapa" (status `pulada`) pra pular de forma explícita e registrada — não existe "pular" implícito.
- **Exclusão com bloqueio**: papel, etapa ou fase só podem ser excluídos se nunca participaram de execução real; senão a UI deve recusar com "Impossível excluir, já em uso".
- **Data de término do contrato** = início + vigência − 30 dias, **só quando a vigência passa de 30 dias** (já implementado em `calcularDataTermino`, `src/components/negociacao-painel.tsx`) — em contrato curto usa a vigência cheia, senão o término cairia no mesmo dia do início.
- **Alerta prévio de 90 dias** só dispara quando a janela faz sentido (num contrato de 90 dias ela cairia antes do início).
- **Multas fixas no contrato**: 5% por descumprimento, 5% de multa moratória, 30 dias de aviso prévio.
- **Foro**: comarca da cidade da empresa contratante, puxada do cadastro.
- **Rejeição na Análise da Solicitação encerra de vez** (só abrindo solicitação nova pra tentar de novo). **Rejeição na Aprovação Interna volta pro Negociador**, não encerra.
- **Negociação Comercial é obrigatória**, não opcional: é o único lugar do fluxo onde fornecedor, valor e objeto do contrato são cadastrados.
- **Correção jurídica centraliza na Elaboração do Contrato**, sem limite de tentativas e sem caminho alternativo pra Negociação (repetido aqui de propósito — é a decisão mais fácil de "corrigir" sem contexto).
- **Renovar repete os mesmos termos** por enquanto; condições diferentes dependem do TAC.
- **SSMA fica de fora das solicitações novas.** Existe uma etapa SSMA órfã na solicitação #5, resquício de quando ela esteve ativa na configuração — decidido deixar como está em vez de fazer limpeza de dado histórico.
- **O TAC (Termo Aditivo Contratual) foi adiado por decisão, não por falta de tempo.** Não é uma feature esquecida no backlog — é escopo conscientemente fechado por ora. Enquanto ele não existir como funcionalidade, o botão Renovar continua repetindo os mesmos termos do contrato (ver acima); isso é consequência aceita da decisão, não um bug a corrigir por conta própria.
- **A Assinatura simulada é intencional, não um placeholder esquecido.** Integração real de assinatura eletrônica (ZapSign, Clicksign ou DocuSign) fica pra quando fechar o primeiro cliente pagante — todas as opções são pagas, então não faz sentido contratar uma antes de ter cliente que justifique o custo. Não trocar por integração real sem alinhar com o usuário primeiro.

## Aprendizados técnicos reutilizáveis

Armadilhas concretas já pisadas neste projeto — a maioria não é óbvia só lendo o código no estado atual, porque a correção já está aplicada e o motivo dela não aparece sozinho.

- **Checar-depois-inserir não é atômico.** `executarCadastroContrato` (`src/motor.server.ts`) checava "já existe contrato pra essa solicitação?" antes de inserir; duas execuções do motor quase simultâneas passavam as duas pela checagem e criavam contratos duplicados pra mesma solicitação. A correção de verdade é no banco, não em mais código de checagem: existe a constraint `contratos_solicitacao_id_key UNIQUE (solicitacao_id)`, e o código trata o erro Postgres `23505` como sucesso (significa exatamente "o que eu ia criar já existe"). Regra geral: condição de corrida entre "ler" e "escrever" se resolve com constraint no banco, tratando a violação como caminho feliz — não com mais uma checagem em código, que só estreita a janela sem fechar.
- **Resolver um dado que ainda não existe dá resultado errado em silêncio, não erro.** É o motivo de `reconciliarAprovadoresPorValor` existir (ver seção do motor, acima): `etapas_execucao` nasce junto com a solicitação, quando `valor` ainda é `null`. Resolver a faixa de alçada nesse instante sempre dava a faixa mais baixa — nenhuma contratação acima do teto subia pro Diretor, e nada quebrava, nem logava erro. Lição: quando um dado necessário pra uma decisão só existe depois, no meio do fluxo, resolver a decisão de novo quando o dado aparece (idempotente, sem tocar no que já foi decidido) é mais seguro que tentar resolver tudo de uma vez na criação.
- **Colocar a lógica no motor evita duplicação entre caminhos.** Os dois caminhos de negociação (link externo do Negociador via token, e painel interno de quem está logado — ver `NegociacaoApi` na seção de arquitetura) terminam os dois chamando `avancarFluxo`. Corrigir comportamento de fluxo ali dentro vale pros dois caminhos hoje e pra qualquer caminho novo no futuro — não duplicar a lógica de avanço de etapa em cada tela que pode disparar o motor.
- **Etapa com mais de dois desfechos não cabe em Aprovar/Rejeitar.** Renovação e Encerramento (e a própria Validação Jurídica) são destinos distintos, não um par binário aceitar/recusar. Daí o mapa `ETAPAS_DECISAO_CUSTOMIZADA` no motor, que roteia o link do e-mail pra uma tela dedicada (`/renovacao/$token`, `/juridico/$token`) em vez de reaproveitar `/aprovacao/$token` com mais um `case`.
- **`types.ts` desatualizado mascara erro de verdade como frescor de tipo.** Numa sessão anterior faltavam no arquivo gerado tabelas inteiras (`aprovacao_tokens`, `negociacoes`) e colunas (`email` em `papeis_empresa`). Regenerar via Supabase MCP (`generate_typescript_types`) derrubou os erros de tipo de 156 pra 13 de uma vez — antes de investigar um erro de tipo estranho em código que parece correto, vale confirmar que `types.ts` realmente reflete o schema atual.
- **`createServerFn` usa `.inputValidator()`, não `.validator()`**, nesta versão do TanStack Start (`^1.167`). É a API que muda de nome entre versões — não assumir a API de posts/exemplos antigos sem checar a versão instalada.
- **Não existe pasta `src/server/`** — o projeto bloqueia importação de qualquer caminho que bata com `**/server/**`. Isso é adicional à convenção de nomear arquivos `*.server.ts` (seção acima): não é só sufixo no nome, é também não organizar esses arquivos numa subpasta chamada `server`. Eles ficam soltos em `src/` (`motor.server.ts`, `minuta.server.ts` etc.) ou dentro de `src/integrations/supabase/`.
- **Rota nova de tela precisa ser irmã, não filha, de uma rota já existente sem `<Outlet />`.** Rota-filha exige que a rota-mãe renderize `<Outlet />` pra ela aparecer. É por isso que `/negociacao/$id` e `/contrato/$id` existem como rotas irmãs de `/solicitacoes/$id`, em vez de aninhadas dentro dela.
- **Rota de API pura** (sem componente React) usa `createFileRoute("/caminho")({ server: { handlers: { GET: async (...) => ... } } })` — ver `src/routes/api.rotina-diaria.ts`. Não é uma rota de UI com um handler a mais; é o padrão pra endpoint puro dentro do file-based routing do TanStack Router.
- **Cron do plano Hobby do Vercel roda 1x por dia, em horário aproximado, em UTC** — não é garantido disparar exatamente às 9h. Não assumir precisão de minuto na rotina diária (`src/rotina.server.ts`).
- **`wrangler.jsonc` pode ser resquício do template da Lovable, não deploy ativo de verdade.** Ficou registrado de uma sessão anterior como incerteza, não confirmado nem descartado: se o cron do `vercel.json` parecer não estar surtindo efeito, vale investigar se o `wrangler.jsonc`/Cloudflare está de alguma forma competindo com o deploy do Vercel antes de mexer no cron em si.
- **Limite de requisições da API do GitHub tem contorno rápido:** baixar o repositório inteiro como tarball via `codeload.github.com` resolve sem precisar de token nem esperar o rate limit resetar:
  ```bash
  curl -sL "https://codeload.github.com/<user>/<repo>/tar.gz/refs/heads/main" -o repo.tar.gz
  ```
